# life-sim 計画書

## 目的

数万体の生物が暮らす 2D 生態系をシミュレートし、それを観察して遊ぶ。
プレイヤーは観察に加えて環境や個体群に介入できる。将来的には、1 個体に乗り移って
その個体として生きるモードも入れたい（オプション）。

## 要件

| 項目 | 要件 |
|---|---|
| 規模 | 数万体（目標: 5 万体を 30 tick/s で回す） |
| 表示 | 2D 俯瞰 |
| 介入 | 餌を撒く、種を投入する、地形・気候を変えるなど |
| 個体操作 | オプション。後から追加できる設計にしておく |
| 開発体制 | Rust は入門レベル。パラメータ調整は Rust を触らずにできるようにする |

## 技術スタック

| 層 | 選定 | 理由 |
|---|---|---|
| シミュレーション | Rust → WASM（Web Worker 上） | 数万体 × ニューラル脳の計算量に耐えるため。最初から Rust で書き、移植の二度手間を避ける |
| JS と WASM の境界 | 素の `extern "C"` export ＋ WebAssembly API | 境界を越えるのは数値とメモリ上のアドレスだけなので、wasm-bindgen / wasm-pack は使わない。依存とビルド手順を減らせる。文字列や構造体の受け渡しが必要になったら導入を再検討する |
| フロント | TypeScript + Vite | 試行錯誤が速く、型で状態の構造を固められる |
| 描画 | PixiJS v8 の ParticleContainer | 10 万スプライト規模向けの描画経路 |
| グラフ | uPlot（Phase 3 で導入） | 軽量で、時系列の描画が速い |

### 採らなかった案

- **WebGPU compute で全部 GPU 計算**: 誕生や死亡で個体数が変わる処理、系統樹やイベント検出、
  介入や憑依のために CPU 側から個体を読み書きする処理が、どれも GPU では扱いづらい
- **TS だけで実装**: 数万体まではいけるが、ニューラル脳を入れると余裕がなくなる
- **Godot / Bevy**: 観察 UI やグラフの作りやすさでブラウザに劣る

## アーキテクチャ

```
┌──────────── メインスレッド ────────────┐      ┌────────── Worker ──────────┐
│ UI（操作・グラフ・インスペクタ）           │ cmd  │ sim.wasm（Rust）            │
│ PixiJS 描画                              │ ───▶ │  - 固定タイムステップ          │
│                                          │ ◀─── │  - SoA の個体データ           │
│                                          │ 描画用 │  - 空間ハッシュ               │
└──────────────────────────────────────────┘ バッファ └────────────────────────────┘
```

### 原則

1. **シミュレーションと描画を分離する**: sim は Worker 内で固定タイムステップで進み、
   描画側は最新のスナップショットを描くだけ。倍速や一時停止はこの構成で素直に実装できる
2. **決定論的にする**: 乱数はシード付きの自前 PRNG を使う。
   シード＋コマンド列で歴史を完全に再現できる（リプレイや共有に使う）
3. **SoA ＋ ゼロコピー**: 個体データは Rust 側の連続配列で持ち、JS は WASM メモリを
   TypedArray で直接参照する
4. **空間ハッシュ**: 近傍探索はグリッドで行う。tick ごとにセルソートで作り直す
5. **描画用バッファは transferable で受け渡す**: 位置と色だけを詰めたバッファを
   Worker から毎フレーム転送する。SharedArrayBuffer は COOP/COEP ヘッダが必要で
   静的ホスティングと相性が悪いため、必要になるまで使わない
6. **ズームに応じて見せ方を変える（LOD）**: 引きでは点と密度、寄るとスプライト

### 脳の出力 ＝ 行動ベクトル（介入・憑依のための核心設計）

```
入力（知覚）: 近くの餌・天敵・仲間の方向と距離、自分のエネルギー …
出力（行動）: 移動方向, 速度, 食べる, 攻撃する, 繁殖する
```

- AI 個体は遺伝子で決まる小さなニューラルネット（例: 12-8-5）がこのベクトルを出す
- プレイヤーが憑依した個体は、キー入力がこのベクトルを出す
- sim から見ると両者は区別がつかない。憑依は「脳の差し替え」だけで実装できる

### 介入 ＝ コマンドキュー

UI からの介入は `{tick, command}` として Worker に送り、tick の境目で適用する。
これで決定論が保たれ、コマンド列を記録すればリプレイになる。

### Rust に不慣れでも触れる構成にする

- 調整用のパラメータ（代謝・繁殖閾値・変異率など）は TS 側の設定ファイルにまとめ、
  起動時に WASM へ渡す。数値を変えるだけなら Rust を触らなくていい
- Rust コードには日本語コメントを付け、ライフタイムやトレイトを駆使する凝った書き方は避ける
- `sim/` の Rust はネイティブでもテストできるようにし、ヘッドレスで長時間回して
  「絶滅しないか」「爆発しないか」を確認できるようにする

## 遺伝子と脳（Phase 2）

遺伝子は「体の形質」と「脳の配線」に分ける。体は何ができるか、脳はそれをどう使うかを決める。
分けておくと、観察したときに「速くなった」のか「逃げ方がうまくなった」のかを区別できる。

### 体の形質

| 遺伝子 | 利点 | 代償 |
|---|---|---|
| 大きさ | 蓄えられるエネルギーと一口の量が増える。肉食は大きい獲物を狩れる | 代謝が大きさの 0.75 乗で増える。小回りが利かない |
| 最高速度 | 逃げる・追うのに有利 | 移動コストが「大きさ × 速度²」で増える |
| 視野 | 早く気づける | 視野に比例して代謝が増える |
| 子への投資 | 子が多くのエネルギーを持って生まれる | 親の手元に残る量が減る |
| 標識色 | なし | なし（生存に影響せず、変異で漂うだけ。系統の広がりを見るため） |

- 寿命は独立した遺伝子にせず、大きさから決める（自由にすると最大化一択になる）
- 肉食が襲えるのは、自分の大きさの一定倍までの獲物だけ（草食が大型化して身を守る余地）
- 食性は Phase 2 では固定。安定したら「植物と肉の消化効率」の遺伝子を足し、草食・肉食の区別そのものを進化に任せる

### 脳

遺伝子で重みが決まる小さなニューラルネット（入力 13・中間 8・出力 4）。

- 入力は自分の向きを基準にした相対値（前方成分・右方成分）にする。どの方向でも同じ配線で振る舞える
  - 自分のエネルギー、いまのマスの草の量、草の多い方向
  - 最寄りの天敵・獲物・仲間の、方向と近さ
- 出力
  - 曲がる量、速さ（最高速度に対する割合）
  - 繁殖するか（必要なエネルギーを満たしているとき）
  - 食べるか（草食は目の前の草、肉食は届く範囲の獲物）
- 最初の脳は手で配線を設計し、Phase 1 の手書きルールとほぼ同じ動きから始める。
  ランダムな脳から始めると、適応する前に全滅する

### 隠れ（植物による被発見率の低下）

相手を見つけられる距離が、相手のいるマスの草の量に応じて縮む。

```text
見つけられる距離 = 自分の視野 × (1 − 隠れの強さ × 相手のマスの草の量 / 上限)
```

- 草食・肉食のどちらにも効く（草むらに潜む草食も、待ち伏せする肉食も成り立つ）
- 「食べる」出力と組み合わさって、草を残して身を隠す戦略が成り立つ（栄養 ⇔ 隠れ場所）
- 確率ではなく距離で表すのは、乱数を引かずに済んで速く、判定が安定するため

### 変異と繁殖

- 子は親の遺伝子をコピーし、各値に小さな正規分布のノイズを足す（変異率と大きさはパラメータ）
- 当面は無性生殖。有性生殖は「相手を探す」行動が要るので後の段階にする

### 近傍探索に四分木ではなく一様グリッドを使う理由

- 全個体が毎 tick 動くので、構造は毎 tick 作り直しになる。グリッドはカウンティングソートで O(n)、
  四分木は O(n log n) でノードの確保も伴う
- グリッドは平坦な配列だけでできていて、キャッシュに乗りやすい。四分木は木をたどるたびに
  メモリ上の離れた場所を読む
- 探索半径がほぼ一定で、密度の偏りも極端ではない。四分木が有利なのは、
  密度の偏りが桁違いに大きい場合や、探索半径が個体ごとに大きく違う場合
- 実測では、ボトルネックは構造の選択ではなくメモリアクセスの順序と分岐の数だった（下記）

遺伝子で視野半径を変えられるようにして、その差が大きくなった場合は、
半径の段階ごとにグリッドを分ける方式（多段グリッド）を先に検討する。

### Phase 2 の結果

既定値（世界 7200×4800、日射量 0.08）で、3 つの seed とも 3 万 tick 共存した。
個体数は振動し、合計は平均 2〜3 万体、ピークで 6 万体台、最小でも草食 1,500 体・肉食 780 体程度。

3 万 tick 後の形質の平均（初期値 → 結果、seed によって進化の道筋が違う）:

| 形質 | 草食 | 肉食 |
|---|---|---|
| 最高速度 | 1.3 → 1.4〜2.4 | 1.8 → 2.6〜3.4 |
| 視野 | 30 → 33〜34 | 48 → 47〜49 |
| 大きさ | 1.0 → 0.86〜1.05 | 1.0 → 1.0〜1.35 |

調整で分かったこと:

- **変異が捕食者を強くしすぎて共倒れになる**。遺伝子 1 個あたり 10% の変異率だと、子は毎回約 15 か所変わり、
  数世代で「速く探し回る肉食」が広がって草食を食べ尽くす。変異率を 2% に下げ、隠れを強め（0.85）、
  肉食の代謝と移動コストを上げて抑えた
- **日射量を上げると振動が大きくなり、かえって絶滅しやすくなる**（富栄養化のパラドックス）。
  個体数を増やすには日射量より世界を広げるほうがよい。広い世界では場所ごとに増減がずれて、全体が安定する
- 脳の出力は「曲がる量」ではなく「行きたい方向」にした。曲がる量だと、天敵が真正面にいるとき曲がれず突っ込む
- 「近さ」の入力は、見えていれば 0.5〜1・見えなければ 0 にした。`1 − 距離/視野` だと視野の端で 0 になり、
  見えていても逃げ始めない

### 群れの検証（2026-11-14）

群れの度合いを 2 つの指標で測る（草食と肉食それぞれ）。

- 集まり具合（Clark-Evans 比）: 最寄りの仲間までの平均距離 ÷ ランダムに散らばった場合の期待値。1 でランダム、小さいほど集まっている
- 向きのそろい: 近く（32px 以内）の仲間との向きの cos の平均。0 でばらばら、1 で同じ向き

集まり具合だけだと「草の多い場所に別々に集まっている」のと区別できないので、向きも見る。

| | 集まり具合 | 向きのそろい |
|---|---|---|
| 草食（群れの知覚なし） | 0.5〜0.9 | 0.3〜0.5 |
| 肉食（群れの知覚なし） | 約 0.6 | 0.35〜0.7 |
| 草食（群れの知覚あり、4 万 tick） | 0.6〜0.9 | 0.3〜0.4 |

- 知覚がなくてもある程度集まり、向きもそろう。同じ天敵から一斉に逃げる、捕食と被食の波が移動する、
  といった共通の状況への反応による。群れの判断はこの基準からの上昇で見る
- 群れの知覚（見えている仲間の数・平均の向き・興奮度）を入力に足し、初期の脳には小さなランダムの配線だけ入れた。
  4 万 tick では群れは生まれなかった。群れると草を取り合う損が、利己的な群れの効果などの得を上回っていると考えられる
- seed 1 では草食が増え続け（9 万 3 千体）、肉食が減り続けた（647 体）。仲間の興奮度を、群れずに各自が早く逃げるために
  使っている可能性がある（1 本だけの結果なので未確定）
- 次は有性生殖を入れる。相手を見つけないと子を残せないので、仲間の近くにいる利益が直接生まれる

### 有性生殖（2026-11-14）

- 繁殖には、相手を探せる距離以内に同じ種類の個体が見えている必要がある。子の遺伝子は両親から
  ニューロン単位で受け継ぐ（重みを 1 個ずつ混ぜると、ニューロンへ入る重みが寄せ集めになって機能が壊れる）。
  エネルギーを払うのは繁殖を決めた側だけ
- 相手を探せる距離は草食 12px、肉食 20px。肉食は密度が低く、12px だと序盤に相手がいる確率が約 4% しかなく、
  ほとんど繁殖できずに 45 体まで減った。40px にすると逆に増えすぎて振動が大きくなった
- 相手が見つからないと増えにくい（アリー効果）ので、無性生殖のときより振動が大きい。
  肉食の最小値は 780 体 → 150〜350 体に下がった。初期個体数を釣り合いに近い値（草食 25,000・肉食 1,500）に下げて序盤の振れを抑えた
- 群れ: 個体数が少ない時期は強く集まる（集まり具合 0.2〜0.4、向きのそろい 0.7〜0.8）。相手が近い集団だけが子を残せるため。
  個体数が戻ると基準の範囲に戻り、群れが続くことはなかった
- 画面で見ると、草を食べ尽くした領域と回復した領域の境目を、草食が前線のように進む波が見える

### 日射量の自動調整（2026-11-14）

計算が重くなったら日射量を少しずつ下げて個体数を減らし、軽くなったら設定値まで戻す（Worker 側で計測）。

- 目標は等倍に必要な時間の 6 割（20 ms/tick）。移動平均がこれを超えたら下げ、8 割を下回ったら戻す
- 変化は tick 数に比例させる（30 tick で 0.25%）。日射量を変えてから個体数が変わるまで数百〜数千 tick の遅れがあり、
  実時間で決めると倍速のときに速すぎて行き過ぎる
- 下限は設定値の 3 割。画面でオン・オフでき、実効値と下げ幅を表示する
- PC の速さで日射量が変わるので、同じ seed でも歴史が再現しなくなる。Phase 4 でコマンド列を記録する仕組みを入れたら、
  日射量の変更も記録して再現できるようにする

### 狩りの成功率と成長（2026-11-14）

- 狩りの成功率 = 最大成功率 0.9 × 大きさの補正 ÷ (1 + 0.15 × 獲物の近くの仲間の数)。
  大きさの補正は「獲物 ÷ 肉食」の比が 0.7 以下で 1、1.5 以上で 0、間は直線
- 襲うたびにエネルギーを 0.3 失い、10 tick は次を襲えない（毎 tick 襲い直せると、失敗しても数 tick で結局成功する）
- 子は「受け取ったエネルギー ÷ 大人が繁殖に必要な量」の大きさで生まれ（下限 0.2）、成熟（草食 600 tick、肉食 900 tick）まで育つ。
  成熟するまで繁殖できず、足も遅い（最高速度 × (0.6 + 0.4 × 成長度)）。代謝・一口の量・蓄えの上限・狩りにはいまの大きさを使う
- 子への投資の遺伝子に「大きく産むか、たくさん産むか」の意味が出た（3 万 tick ではまだ 0.50 から動いていない）
- 世界を 4800×3200 に戻し、日射量を 0.06 に下げた。3 つの seed とも 3 万 tick 共存し、平均の合計は 1.5〜2 万体、
  WASM で 1.5 万体のとき約 5 ms/tick
- 狩りの成功率を 0.8 にしたときは、肉食が弱すぎて 3 体まで減る seed があった

### 系統と種分化（2026-11-15）

- 遺伝的距離（標識色を除く全遺伝子の差を、変異 1 回の大きさで割った二乗平均の平方根）が 1.2 を超えると繁殖が失敗しやすくなり、
  2.5 で失敗確実。失敗しても繁殖のコストは払う。初期個体の仲間への配線は種類ごとに共有する（個体ごとに引くと最初から交配できない）
- 脳の入力に、標識色が近い仲間の方向と割合を加えた（系統を見分ける手がかり）
- 10 万 tick で交配の失敗率は 15〜32% まで上がり、種が分かれる兆しが出た。系統ごとの群れは生まれなかった
- 肉食は 6〜8 万 tick で絶滅した。相性による失敗を切った比較でも 8 万 tick 前後で絶滅したので、主な原因は相性ではなく、
  草食の小型化・高速化に肉食が負ける軍拡競争（小さい獲物は割に合わない）

### 欲求と優先度（2026-11-15）

進む方向は、欲求ごとの方向を脳が出す優先度で混ぜて決める。方向は固定のルール、優先度の付け方が遺伝子。
「繁殖できるときだけ相手へ向かう」のような条件付きの行動は、小さなネットが変異だけで作り上げるのは難しいため。

| 欲求 | 方向 | 初期の優先度の付け方 |
|---|---|---|
| 食べる | 草食: 草の多い方へ / 肉食: 獲物へ | 空腹で高く、満腹で低い |
| 繁殖 | 繁殖相手（成熟した仲間、標識色が近い個体を優先）へ | 繁殖できる状態で高い |
| 逃げる | 天敵と反対へ。見えていなければ、逃げている仲間の向きへ（警戒の合図） | 天敵が見えたら、または仲間が逃げたら最優先 |
| 仲間 | 見えている仲間の中心へ | 低い（進化に任せる） |
| 自由 | 脳が決める方向へ | 中くらい |

加えて、草食は警戒の度合い（高いほど天敵に遠くから気づけるが一口が小さい）を出す。

### 現実の生態系をもとにした調整（2026-11-15）

調べたこと:

- 哺乳類の肉食は、獲物 1 万 kg あたり約 90 kg（量で約 1/111）しか養えない（Carbone & Gittleman 2002、Science）。比はばらつく
- 栄養段階の受け渡し効率は平均 10% 前後（5〜20%）
- 狩りの効率が獲物の多さに比例して伸び満腹で頭打ちになる形（II 型）は振動を大きくし、獲物が少ないと効率が落ちる形（III 型）や
  獲物の避難所は振動を落ち着かせる傾向がある（条件しだいで逆もある）。多くの捕食者は消化の速さで食べる量が決まる
- 群れの利点は、薄め効果・利己的な群れ・多くの目（見張りの分担で各自が食べる時間を増やせる）。群れが大きいほど 1 頭の見張りは減る
- 肉食は自分の体重の半分〜2 倍の獲物を好む

決めたこと:

- 量の比の目標は 1/20〜1/40（現実の 1/111 だと、この世界の広さでは肉食が少なすぎて偶然の揺れで絶滅する）、受け渡し効率の目標は 10%
- 肉食どうしの干渉（近くに別の肉食がいると狩りの成功率が下がる）を入れた。混み合ったときだけ効くので、絶滅の危険を上げずに増えすぎを抑えられる
- 肉食の効率を 0.5 → 0.4。量の比 1/27〜1/29、草食 → 肉食の効率 9%（2 万 tick、2 seed）。0.35 以下では肉食が絶滅し、境目は狭い
- 警戒の合図と相手探しを入れると、群れがはっきり出た（集まり具合 0.24〜0.36、向きのそろい 0.65〜0.76。知覚なしの基準は 0.5〜0.9 と 0.3〜0.5）。
  肉食を減らして草食が増えると、どちらも 0.55 前後に下がる

- 肉食の効率 0.4 で 10 万 tick を回すと、4〜5 万 tick で草食の高速化（1.3 → 1.9）が進み、肉食が 144 体まで減った。
  原因は「最高速度がほぼ無料」なこと。移動コストは実際に走った速さで決まり、草食は普段ゆっくり食べていて全力で走るのは逃げるときだけなので、
  速く走れる体を持つ費用がほとんどかからない
- 最高速度の維持費（走っていなくてもかかる、最高速度 × 大きさの 0.75 乗に比例）を入れた。初期の速さで代謝の合計が変わらないよう基本の代謝を下げた
  （草食 0.0076 → 0.005、肉食 0.011 → 0.0074）。日射量は 0.06 → 0.045（個体数を減らして計算を軽くし、振動も抑える）
- 6 万 tick・2 seed で、肉食の最小値は維持費なし 143〜292 体 → あり 311〜395 体。量の比は 1/17〜1/60 の間で揺れる
- 草食の高速化は止まらない（6 万 tick で 1.65〜1.89）が、肉食も 2.3〜2.6 に速くなって追いついている
- 群れは序盤だけ強く（集まり具合 0.6、そろい 0.55）、世代が進むと基準の範囲に戻る（1.0 前後と 0.4 前後）。仲間に寄る欲求の優先度は、
  進化で強まっていない

### 肉食の群れ（2026-11-15）

肉食が群れなかった理由: 近くの肉食がすべて狩りの邪魔をし（干渉）、協力しても成功率は上がらず、獲物は 1 体で全部食べ、
大きな獲物もいない。群れることに得がなく、損だけがあった。場所の記憶もないので、一定のエリアで狩ることも表現できない。

入れたもの:

- 協力して狩る: 近く（20px）の仲間（同じ系統の肉食）1 体ごとに、獲物から見た自分の大きさが 1.3 倍、1.6 倍…となる（最大 4 体）。
  1 体では倒せない大きな獲物も倒せる
- 獲物を分け合う: 仕留めた獲物を、自分と近くの仲間で等分する
- 干渉は系統の違う肉食だけに効く（獲物の横取りや縄張り争い）

- 肉食の群れは最後まで続いた（集まり具合 0.36〜0.58、向きのそろい 0.57〜0.93、同じ系統どうし 0.59〜0.93）。

- 3 seed とも肉食は生き残ったが、最小値は 78 体（協力なしでは 311〜395 体）。序盤に肉食が増えすぎ（量の比 1/7）、反動で大きく落ち込む

### 季節・繁殖期・弱り（2026-11-15）

### 草食が小さくなる理由の測定（2026-11-16）

`examples/herb_size` で、草食を大人の大きさで段階に分け、1 体・1,000 tick あたりの誕生・襲われた数・死因を測った（シード 1・3、12 万 tick）。

シード 3 の 56,000 tick（肉食 847 体）:

| 大きさ | 割合 | 生 | 襲われた | 食べられた | 逃げきった割合 | 飢え | 純（生 − 死） |
|---|---|---|---|---|---|---|---|
| 0.5〜0.65 | 1% | 1.00 | 0.78 | 0.58 | 0.26 | 0.12 | +0.08 |
| 0.65〜0.8 | 21% | 1.03 | 0.72 | 0.53 | 0.27 | 0.13 | +0.11 |
| 0.8〜1.0 | 64% | 0.97 | 0.96 | 0.66 | 0.31 | 0.09 | +0.01 |
| 1.0〜1.2 | 14% | 1.03 | 1.35 | 0.84 | 0.38 | 0.08 | −0.09 |
| 1.2〜 | 1% | 1.05 | 2.07 | 0.98 | 0.52 | 0.06 | −0.14 |

- 生まれる数は大きさでほとんど変わらない
- **大きい草食ほど襲われる**（1.2 以上は 0.5〜0.65 の約 2.5 倍）。襲われたときに逃げきる割合は大きいほど高いが、襲われる回数の差がそれを上回り、食べられる数は大きいほど多い
- 飢えは小さいほうがやや多い（終盤は差が開く。12 万 tick で 0.5 未満 0.44、0.8〜1.0 で 0.30）が、食べられる差のほうが大きい
- シード 1 も同じ傾向（56,000 tick で 1.2 以上が 2.07、0.5〜0.65 が 0.89）。ただしシード 1 の終盤は、0.5 未満が逆によく襲われるようになった（肉食が小さな獲物に合わせた可能性）

小さくなる主な理由は**見つかりにくさ**。見えにくさが 1 / √大きさ に比例する（大きさ 0.6 と 1.2 で 1.4 倍の差）ので、
小さい草食は肉食に見つかる距離が短い。草食が小さくなるほど肉食は獲物を見つけられなくなり、草食が増えすぎる流れにつながる。

### 見つかる距離を体長に比例させる（2026-11-16）

根拠: 見つけられる距離は相手の見かけの大きさ（視角）で決まり、体長に比例する。この sim の大きさは体重にあたる
（代謝が 0.75 乗、寿命が 0.25 乗）ので、体長は大きさの 1/3 乗。これまでの「視野 × (1 − 隠れ × 草 × 1/√大きさ)」は、
草が茂るほど差が極端になり（草 0.8 で 0.6 と 1.2 の差が 3.1 倍）、草のない場所では差が出なかった。
「視野 × 大きさ^(1/3) × (1 − 隠れ × 草)」に変えた（conceal_size_power = 1/3）。

| シード | 肉食 56k | 104k | 120k | 草食の大きさ 120k |
|---|---|---|---|---|
| 1 | 701 | 451（変更前: 429） | 374（111） | 0.59 |
| 2 | 641 | 316（269） | 407（197） | 0.62 |
| 3 | 803 | 139（389） | 295（411） | 0.59 |

草食の大きさごとの測定（シード 3、56k）: 1.2 以上の草食が襲われる回数は 0.5〜0.65 の 1.8 倍（変更前 2.65 倍）に縮んだ。
それでも大きい草食ほど襲われ、逃げきる割合は 1.2 以上でも 49%。草食は同じように 0.6 前後まで小さくなった。
理論に沿った形なので採用。草食が小さくなるのを止めるには、現実の「大きさの逃げ場」（大きい草食ほど捕食されにくい。
Sinclair ほか 2003）が足りない。

### 捕食のない世界で草食が小さくなる理由（2026-11-16）

`examples/herb_size` を `carn_initial=0` で回した（シード 1・3）。草食は 12 万 tick で 0.63〜0.65 まで小さくなる。
草を食べた回数と量も大きさの段階ごとに数えるようにした（不足: その場所の草が一口に足りなかった割合、取得: 実際に食べた量 ÷ 一口）。

80k の値（2 シードの範囲。生まれる数は 1 体・1,000 tick あたり）:

| 大きさ | 生まれる数 | 餓死 | 蓄え | 不足 | 取得 |
|---|---|---|---|---|---|
| 0.5〜0.65 | 0.74 | 0.27〜0.30 | 0.75 | 0.85〜0.87 | 0.34〜0.36 |
| 0.65〜0.8 | 0.69〜0.70 | 0.29〜0.31 | 0.72〜0.73 | 0.88〜0.89 | 0.32〜0.33 |
| 0.8〜1 | 0.62〜0.63 | 0.31〜0.32 | 0.70 | 0.91〜0.92 | 0.30〜0.31 |
| 1〜1.2 | 0.51 | 0.31 | 0.68〜0.76 | 0.90〜0.91 | 0.29 |

- 死に方は大きさでほとんど変わらない。差は生まれる数で、小さいほど多く産む
- **草を食べようとした 85〜92% で、その場所の草が一口に足りない**。一口は大きさに比例するが、取れる量は草の量で頭打ちになる。
  大きい草食ほど一口のうち取れる割合が低く（0.29 対 0.36）、大きい口の得がほとんど消えている
- 一方、繁殖・出産・体を作る費用は大きさに比例し、維持費は 0.75 乗。取れる量がほぼ同じで費用だけが大きさに比例するので、小さいほうが得になる
- 草が食べ尽くされている状態（草食が 3〜4 万体）そのものが、草食を小さくしている

現実で大きい草食を支えている仕組みで、この sim にないもの:

- 消化の効率が大きさとともに上がる（腸に長くとどめられる。ジャーマン・ベルの原理。滞留時間は体重の約 1/4 乗）。
  質の低い草でも元が取れる
- 移動の費用が体重あたりで割安になる（体重あたりの移動費は体重の約 −0.3 乗。Taylor ほか 1982）。
  大きいほど遠くの草まで歩いて行ける。今は移動費が大きさに比例し、体重あたりでは同じ

### 植物の高さの層（2026-11-17 設計）

ねらい: 草が食べ尽くされると大きい口が無駄になり、小さいほうが勝つ循環を断つ。現実では体の大きさの違う草食が、
同じ場所の別の高さの葉を食べて共存している（採食の高さの住み分け。du Toit 1990）。高い所は大きい体だけが届く。

仕組み:

- 植物のマスを 3 つの層に分ける: 地面の草・低い茂み・高い枝。層ごとに量を持ち、日射と上限を
  50% / 30% / 20%（plant_share_shrub、plant_share_tree）で分けて、それぞれ育つ。全体の上限と日射は今と同じ
- 届く高さは体長（今の大きさの 1/3 乗）。層ごとに、届く割合が「届き始め」から reach_width の幅でなめらかに 0 → 1 に増える。
  茂みは 1/3 乗が 0.85（大きさ約 0.6）から、枝は 1.05（大きさ約 1.16）から届き始める。地面の草には誰でも届く。
  幼体は今の大きさで決まるので、低い層しか食べられない
- 層の質: 茂みと枝は硬く、身になる割合が低い（地面 1.0、茂み 0.85、枝 0.7 を消化の効率に掛ける）。
  大きい体は量の多い粗い餌、小さい体は少ない良い餌、というジャーマン・ベルの原理の形になる
- 一口は、届く層のうち「届く量 × 質」が最も大きい層から取る（判断に乱数を使わない）
- 脳への入力（周りの草の量・草の多い方向）は、自分が届く層の「量 × 質」で数える。入力の数は変えない
- 草の隠れ（見つかりにくさ）は、今までどおり層の合計の量で決める
- マスの合計の量（biomass）は層の和として持ち続け、描画・隠れ・帳簿はそれを使う。保存は層ごとに書く（保存形式の番号を上げる）

#### 季節で動く植生

- 気温の季節変化: 気温 = 平均気温 ＋ 季節の振れ幅 × 季節。振れ幅は暖かい中央（赤道）でほぼ 0、寒い端（極）ほど大きい
- 植物の育ちやすさを、今の気温で数十 tick ごとに計算し直す。冬は端の寒い地域で草がほぼ育たず、夏は端まで豊かになる
- 動物の体温を保つ費用も、今の気温で決まる
- 草食が生まれた場所で覚える「植生の種類」は、季節で変わらない土の性質にする。育ちやすさ（量）だけが季節で変わる
- 今の「日射の全体の増減」は、この地域差のある季節に置き換える（両方あると効果が二重になる）
- 後の候補: 季節で南北に動く雨の帯（雨季と乾季。毎年決まった経路の大移動が出やすい）

#### 特定の系統の統計

「系統」は、標識色（生存に影響しない、親から子へ少しずつずれる遺伝子）の近さで決める。今の群れの指標と同じ定義で、
新しい記録を持たずに済む。祖先をたどる本当の系統樹は、親の id を持たせれば後から作れるが、記録が膨らむので後回しにする。

- 系統の選び方: 系統色のヒストグラムの棒をクリック、または個体の詳細パネルの「この個体の系統」ボタン（その個体の標識色 ± 一定幅）
- 選んだ系統について表示するもの:
  - 個体数の推移（全体の個体数のグラフに重ねる）
  - 形質の平均（大きさ、速度、視野、好みの気温、子への投資、繁殖シグナル）と、種類全体の平均との差
  - 生まれた数と死因ごとの死亡数（区間ごと）
  - 世代の平均
  - ほかの系統との交配の失敗率（種が分かれつつあるか）
  - 分布: 地図上で、その系統の個体だけを強調する（今の強調表示の仕組みを使う）。重心と広がりの数値も出す
- 計算は Rust 側で行う。選んだ系統（色相の中心と幅）を JS から渡し、統計をまとめて返す関数を足す。
  全個体を 1 回なめるだけなので、0.5 秒ごとの集計なら負担は小さい
- 推移の記録は Worker 側で持つ（今の個体数のグラフと同じ方法）

### 性能

WASM（Node で計測）で 5 万 3 千体のとき 24〜32 ms/tick。等倍（33 ms）にぎりぎり収まり、
6 万体のピークでは一時的に等倍を割る（計算は別スレッドなので、描画と操作は止まらない）。
ネイティブの内訳は、近傍探索 7 ms・脳 2.6 ms・その他 7 ms。
根本的には近傍探索のマルチスレッド化（rayon + SharedArrayBuffer）で解決する。
これには COOP/COEP ヘッダが要るので、公開方法と合わせて検討する

#### 計算時間の調査（2026-11-17）

ネイティブ、並列なし、シード 1 の 6,000 tick（草食約 1.2 万体）を `--features profile` で測った（計測自体の負担を含む）。

| 段 | 割合 |
|---|---|
| 判断（知覚と脳） | 81% |
| 行動（食べる・狩る・争う・相手探し） | 11% |
| 代謝・繁殖 / 移動 / マス目・呼び声 / その他 | 3% / 2% / 2% / 2% |

判断の段の内訳: 脳 44%、草の量と方向・遠くの景色 28%、知覚（視野の中の個体を探す）19%、その他の入力 9%。
並列ありでは判断の段が 9 倍速くなり、順番に処理する行動の段が全体の約半分になる（1 体あたり約 130 ns で、詰める余地は小さい）。

ブラウザ（WASM、並列なし）は開いて 730 tick で 7.8 ms/tick（等倍の予算 33 ms に対して 4.3 倍の余裕）。
個体が増えて脳が育つ後半や、速度を上げたときに詰まる。ネイティブとは世界の設定が違うので、この数字では速さを比べられない。

速くする手の候補（効き目の見込み。まだどれも手を付けていない）:

1. 判断の段の計算を削る（ブラウザと画面なしの検証の両方に効く。結果は変えない）
   - 草の入力: 1 体の判断の中で届く高さ（立方根）と食べ残す高さ（累乗）を何度も計算し直している。tick の初めに 1 体 1 回だけ計算しておく
     （判断の段の前に作るので、判断の段で世界を書き換えない決まりは守れる）。遠くの景色は 9 区画 × 植生の合い具合を毎 tick 比べている
   - 脳: 1 体約 0.6 µs。重みの並べ方を変えて SIMD に乗せる
   - 両方で判断の段が約 4 割減り、全体で 1.4〜1.6 倍の見込み
2. ブラウザで判断の段を並列にする（WASM のスレッド）。8 スレッドで全体約 3 倍の見込み（判断の段 81% から）。
   nightly でのビルド、スレッドの仕組み（今の WASM は wasm-bindgen を使っていないので、wasm-bindgen-rayon なら作りの変更が大きい）、COOP/COEP ヘッダが要る。
   GitHub Pages はヘッダを設定できないが、Service Worker でヘッダを付け直す coi-serviceworker（1 ファイル、MIT）で回避できる。
   初回に 1 回再読み込みが入り、Service Worker が使えない環境では並列なしで動かす必要がある
3. サーバーとクライアントに分ける。計算はネイティブ（rayon で並列）で行い、ブラウザは WebSocket で表示と操作だけにする。
   画面とワーカーはメッセージ（ToWorker / FromWorker）だけでつながっているので、同じメッセージを WebSocket で送り受けする部品に差し替えればよい。
   ワーカーの処理（約 590 行）を Rust に移す。ネイティブの並列ありは並列なしの 3.5 倍速いので、効き目は最も大きい見込み。
   画面なしの検証を回しながらブラウザで覗けるようにもなる。GitHub Pages だけでは動かない（手元でサーバーを起動する。公開版は WASM のまま）。
   1 フレームは個体 1.5 万体で約 46 万バイト、30 回/秒で 14 MB/秒。同じ PC や LAN なら問題ないが、インターネット越しなら縮める工夫が要る。
   WebSocket は tungstenite などのクレートか、標準ライブラリだけで書く（新しい依存は入れる前に確認する）

描画の補間（tick の間を移動量で補う）は動きを滑らかにするだけで、計算待ちは減らないので後回し。

### Phase 1 の結果

既定値（日射量 0.08）で、草食 約 3.7 万・肉食 約 2.9 千・植物量 1〜2 千が、1 万 2 千 tick 以上共存した。
日射量を 0.1 にすると草食 約 4.7 万・肉食 約 3.3 千になり、日射量で個体数が決まることを確認した。

- 世界全体の個体数は振動せず、ほぼ一定で落ち着く。場所ごとに増減のタイミングがずれていて、
  全体では打ち消し合っているとみている。局所的な波として見えているかの確認は、Phase 3 の観察 UI で行う
- 肉食を強くしすぎると（追跡速度 2.0 など）、草食を食べ尽くしたあと肉食も全滅する
- バランス調整は `cargo run --release --example headless --manifest-path sim/Cargo.toml -- 12000 名前=値` で
  画面なしに行える

### Phase 0 の計測結果

世界は 4800×3200 で固定、近傍半径は 16px、WASM（Node で計測）:

| 個体数 | ms/tick | 最大 tick/s |
|---|---|---|
| 1 万 | 0.53 | 1887 |
| 5 万 | 3.35 | 298 |
| 10 万 | 7.79 | 128 |
| 20 万 | 19.78 | 51 |

ブラウザ（ヘッドレス Edge、ソフトウェア GL）では、5 万体・20 万体のどちらでも描画 60fps を確認した。

効いた最適化（5 万体の近傍探索、ネイティブ計測で 5.25 → 1.54 ms）:

1. 全個体のループをセル順に回す（近くの個体を続けて処理し、触るメモリを再利用させる）
2. 端での折り返しに剰余（`%`）を使わない（割り算は遅い）
3. 同じ行で横に並ぶ 3 セルは items 上で連続しているので、1 区間としてまとめて回す
4. 自分自身を if で除外せず、全部数えてから 1 引く（分岐を減らす）

座標をセル順に並べたコピーを持つ方法は、単体では効果がほぼなかった（上記 1〜4 の前提として残している）。

世界の広さが固定だと、個体を増やすほど 1 体あたりの近傍数も増え、計算量は
個体数の 2 乗に近づく。ただし個体数に上限は設けない。個体数は地表に届くエネルギー量で
自然に決まるようにする（下記「エネルギーの流れ」）。

## エネルギーの流れ（Phase 1 以降の基本ルール）

個体数を人工的な上限で止めない。エネルギーの流れを「太陽 → 草 → 草食 → 肉食」の一方通行にし、
生きているだけで熱として失うようにすれば、養える個体数は自然に決まる。

```text
養える個体数 ≒ 地表に届くエネルギー量 ÷ 1 体が生きるのに使うエネルギー量
```

- 主な調整項目は日射量（地表に届くエネルギー量）。これで個体数を調整する
- 季節は日射量を時間で変えるだけで表現できる。地域によって変えれば、豊かな土地と痩せた土地ができる
- 介入ツールとして「この一帯の日射を強くする」がそのまま使える
- 日射量を上げれば個体数が増え、計算も重くなる。その重さは計測パネルの「余裕」に表示する
- 地形を入れる段階（Phase 5）で、地熱も第 2 のエネルギー源として検討する。日の当たらない場所に、
  地熱で生きる別系統の生態系（熱水噴出孔のようなもの）ができる余地がある

### エネルギーを湧かせないためのルール（守らないと個体数が際限なく増える）

- 子どものエネルギーは親から分け与える（合計は増えない）
- 食べられた側のエネルギーは、一部だけが食べた側に移る（残りは熱として失われる）
- 代謝や移動で使ったエネルギーは熱として失われる
- 死体のエネルギーは土に戻すか、そのまま消す
- エネルギーの総量（＝流入した量 − 失われた量）が帳尻に合うことを、テストで監視する
